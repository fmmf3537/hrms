## 一、外部服务成本估算

### 1.1 估算口径

- **员工规模**：100 人（V1.2 §1.2 中期目标）
- **AI 能力调用量**：按每人每天 3 次 AI 调用（OCR / QA / 摘要 / 评分建议）估算
- **数据规模**：100 人 × 60 字段档案 + 月度考勤/算薪/绩效，约 10 GB/年
- **调用量**：年度外部服务总调用量约 12 万次（不含电子签，电子签见单独预算）

### 1.4 成本优化建议

1. **LLM 选国产替代**：DeepSeek / 通义千问 / 文心一言，按 token 价格降 50-80%
2. **缓存 AI 答案**：高频问题缓存到 Redis（节省 30% LLM 成本）
3. **OCR 仅在必要时用**：本地正则可识别的字段（如身份证格式校验）不调 OCR
4. **监控告警频次降级**：非工作时间合并告警
5. **季度复盘**：每季度评估用量趋势，调整套餐

### 1.5 预算审批流程

- 单月超预算 20% 内：HR 主管审批
- 单月超预算 20%-50%：CTO 审批
- 单月超预算 50%+：总经理审批 + 季度专项复盘
- 年度预算由总经理签字，季度复盘调整

## 二、数据生命周期完整 SOP

### 2.1 数据保留期一览

源自 V1.2 §八.2：

| 数据类别 | 保留期 | 法律依据 | 存储位置 |
|---|---|---|---|
| 在职员工档案 | 全量保留（在职期间） | — | PostgreSQL `employees` |
| 离职员工档案 | **5 年** | 劳动法 | PostgreSQL `employees`（软删除 + 归档标记）|
| 考勤数据 | **3 年** | 内部规定 | PostgreSQL `attendance_records` |
| 薪酬数据 | **10 年** | 税法 | PostgreSQL `payslips` |
| 审计日志 | **3 年** | 等保三级 | PostgreSQL `audit_logs` |
| 合同扫描件 | 离职后 5 年 | 劳动法 | OSS 对象存储 |
| 工资条 PDF | 5 年 | 内部规定 | OSS 对象存储 |
| 通知日志 | 1 年 | 内部规定 | PostgreSQL `notification_logs` |

### 2.2 日常归档策略

#### 2.2.1 月度归档

**时机**：每月 5 日算薪完成后

**执行**：
1. BullMQ 定时任务自动触发
2. 归档上月的考勤、算薪、绩效数据到 `archives_y2026m08` 分区表
3. 写归档日志（`archive_logs` 表）记录：归档时间、执行人、数据条数、数据起止日期
4. 通知 HR 归档完成

**自动化实现**：
- BullMQ cron job：`0 0 5 6 * *`（每月 6 日 0 点）
- 脚本路径：`server/src/jobs/archive-monthly.job.ts`
- 失败重试 3 次，失败告警到钉钉/飞书

#### 2.2.2 季度归档

**时机**：每季度第一个月 10 日

**执行**：
1. 归档上季度的合同变更、调动记录、绩效考核结果
2. 校验上季度数据的完整性（与上季度报表交叉对账）
3. 输出"季度数据完整性报告"给 CTO

#### 2.2.3 年度归档

**时机**：次年 1 月 31 日前

**执行**：
1. 归档全年数据到 `archives_y2026` 年度表
2. 删除保留期满的旧数据（见 §2.3）
3. 备份全量数据到冷存储（OSS 低频访问层）
4. 输出"年度数据归档报告"

### 2.3 保留期满操作

| 数据类别 | 保留期满后操作 | 自动化程度 |
|---|---|---|
| 在职员工档案 | 不适用（在员工离职时进入 5 年保留期） | — |
| 离职员工档案（5 年）| 自动从主表移到 `archived_employees` 表，再过 5 年物理删除 | 半自动 |
| 考勤数据（3 年）| 自动物理删除（超过 3 年的月度分区表 DROP） | 全自动 |
| 薪酬数据（10 年）| 自动移到冷存储（OSS）+ 数据库主表保留聚合 | 全自动 |
| 审计日志（3 年）| 自动移到冷存储 + 摘要索引 | 全自动 |
| 合同扫描件（5 年）| OSS 自动设置 lifecycle 规则，5 年后转归档存储，10 年后删除 | 全自动 |
| 工资条 PDF（5 年）| 同上 | 全自动 |
| 通知日志（1 年）| 超过 1 年自动物理删除 | 全自动 |

### 2.4 删除前审批流

#### 2.4.1 必须审批才能删除的数据

- **离职员工档案**：超过 5 年想物理删除 → CTO + 法务 双审批
- **薪酬数据**：任何情况都不允许物理删除（10 年保留期是硬约束）
- **合同扫描件**：超 10 年想删除 → CTO + 法务 + 总经理 三审批

#### 2.4.2 审批流程

走 M0.5-1 审批流基础设施：
1. 系统自动生成"数据销毁申请"实例
2. 申请附：数据范围、销毁原因、销毁方法（物理删/移冷存储/匿名化）
3. 审批链：数据 owner（HR）→ CTO → 法务 → 总经理（按数据敏感度）
4. 审批通过后系统执行销毁
5. 销毁后写"数据销毁记录"（永久保留，不可删）

#### 2.4.3 销毁记录字段

```
data_destruction_records
- id (uuid)
- data_category (string)  # employee_archive / payroll / contract / ...
- record_count (int)
- destruction_method (string)  # physical_delete / cold_storage / anonymize
- approver_ids (json)
- executed_at (timestamp)
- executed_by (uuid)
- retention_period (int)  # 实际保留年限
- reason (text)
- created_at (timestamp)
```

### 2.5 出库审计

#### 2.5.1 哪些操作算"出库"

- 导出 Excel / PDF / CSV 报表
- 批量下载员工档案 / 工资条
- 备份文件下载
- 通过 API 批量拉取敏感数据

#### 2.5.2 出库审计字段

写入 `audit_logs` 表（不另设出库表，复用审计基础设施）：

| 字段 | 说明 |
|---|---|
| action | `EXPORT` |
| resourceType | `Employee` / `Payroll` / `Attendance` 等 |
| description | "导出 100 名员工档案" |
| oldValue | `null` |
| newValue | JSON：导出条件、导出条数、文件大小 |
| status | SUCCESS / FAILURE |
| 关联 IP / UA | 自动记录 |

#### 2.5.3 出库审批

- **< 100 条记录**：HR 可直接导出
- **100-1000 条**：HR 主管审批
- **> 1000 条**：CTO 审批 + 出库理由书面记录
- **全员数据导出**（> 80% 员工）：必须走 M0.5-1 审批流，HR + CTO + 总经理 三签

#### 2.5.4 出库频率预警

- 同一用户 24 小时内出库 > 5 次 → 告警
- 同一用户 7 天内出库总量 > 员工总数 × 50% → 自动锁定账号 + 通知 CTO

## 三、Bug 响应 SLA

### 3.1 故障分级

| 级别 | 名称 | 定义 | 典型场景 |
|---|---|---|---|
| **P0** | 紧急 / 宕机 | 系统不可用 / 数据丢失 / 安全漏洞被利用 | 服务 5xx 全挂；数据库被删；token 泄露 |
| **P1** | 高 / 核心功能不可用 | 核心业务功能 100% 不可用，但系统其他部分可用 | 登录失败；算薪主流程挂；工资条发不出 |
| **P2** | 中 / 非核心 bug | 非核心功能 bug / 性能严重下降 | 导出报表乱码；OCR 偶发失败；筛选条件失效 |
| **P3** | 低 / UI/文案小问题 | 视觉问题 / 文案错别字 / 体验细节 | 按钮错位；提示文案不通顺；图标缺失 |

### 3.2 响应与修复时间

| 级别 | 首响时间 | 修复 SLA | 临时方案（SLA） | 通知范围 |
|---|---|---|---|---|
| **P0** | **5 分钟** | **2 小时** | 30 分钟内 | 全员（钉钉/短信/电话）|
| **P1** | **30 分钟** | **8 小时**（工作时间内）| 4 小时内 | 受影响部门 + IT + HR 主管 |
| **P2** | **4 小时** | **2 工作日** | 下个工作日内 | 业务方 + IT 团队 |
| **P3** | **1 工作日** | **下个迭代** | 不需要 | 工单系统记录 |

### 3.3 响应流程

#### 3.3.1 发现渠道

- 用户报修（HR 微信群 / 工单系统 / 邮件）
- Sentry 自动告警
- 监控告警（Prometheus + Grafana）
- 内部测试发现

#### 3.3.2 响应动作

1. **接单**（首响内完成）
   - Sentry 告警自动创建 Jira / Linear 工单
   - 接单人认领（on-call 工程师 5 分钟内认领，未认领升级）
   - 在 `#hrms-incidents` Slack/钉钉 群发"P0 故障：xxx"

2. **定级**（P0 5 分钟内）
   - 接单人 + CTO 共同定级
   - 高争议走"安全/数据"维度：影响数据安全/隐私的强制升级

3. **修复**（按 SLA）
   - P0 立即拉紧急群（CTO + on-call + 相关工程师）
   - 修复中持续更新状态（每 15 分钟一次）
   - 修复后立即部署（绕过常规流程）

4. **复盘**（P0/P1 必做）
   - 24 小时内开复盘会
   - 写 Post-Mortem 文档（无指责文化，重点是改进）
   - 跟进 action items

#### 3.3.3 升级机制

| 触发条件 | 升级动作 |
|---|---|
| P0 超过 30 分钟未修复 | CTO 直接接管，召集全员 |
| P1 超过 4 小时未修复 | 通知总经理 |
| P2 超过 1 工作日未修复 | IT 主管跟进 |
| 任何故障对客户/员工造成数据影响 | 立即通知法务 + 启动应急响应 |

### 3.4 责任分工

| 角色 | 责任 |
|---|---|
| **On-call 工程师** | 7×24 轮值，首响、修复、写复盘 |
| **CTO** | P0 决策、对外沟通、跨团队协调 |
| **HR 主管** | 业务影响评估、用户通知 |
| **法务** | P0 安全 / 数据事故介入 |
| **总经理** | P0 超 2 小时升级通知 |

### 3.5 故障预防

- **Sentry + APM 7×24 监控**：异常自动告警
- **变更前评审**：所有上线必须 code review + 测试通过
- **灰度发布**：核心功能灰度 5% → 50% → 100%
- **回滚预案**：每次发布必须能 5 分钟内回滚
- **定期演练**：季度故障演练 1 次（chaos engineering）

### 3.6 故障统计与改进

- 月度故障统计：P0/P1/P2/P3 数量、平均修复时间、SLA 达成率
- 季度趋势分析：高频故障点、改进优先级
- 年度回顾：SLA 合理性、流程优化
