## 3. 必读约束

1. **实读先行**：动手前实读 `server/src/services/employee.service.ts`（重点：CreateEmployeeInput 全字段、createEmployee 的校验与副作用、getEmployeeByEmployeeNo）、`server/prisma/schema.prisma` 的 Employee model、`server/prisma/seed.ts` 的部门/公司种子段。字段类型与枚举值以代码为准，不要猜。
2. **幂等设计**：以**工号**为去重键——导入前 `getEmployeeByEmployeeNo()` 存在则跳过（报告计"跳过"），保证同一文件跑两遍不产生重复数据（双跑校验的依据）。
3. **工号保留**：模板中「工号」必填。createEmployee 不接受 employeeNo 入参，故策略 = 先 createEmployee（自动生成临时工号）→ 再 `prisma.employee.update` 改回 Excel 工号（改前查重）。两步必须包在同一个 `prisma.$transaction` 里或补偿式回滚（改工号失败则 deleteEmployee 刚建的记录并报错该行）。把最终采用的方案与理由写进报告。
4. **错误收集**：校验阶段收集**所有行**的错误一次性输出（行号 + 字段 + 原因），不要遇错即停；有任何一行校验失败则整个文件不入库（dry-run 报告原样输出错误清单）。
5. **枚举映射**（模板说明 sheet 与脚本共用一份映射表）：
   - 性别：男/女 → male/female
   - 合同类型：正式/实习/顾问/劳务 → formal/intern/consultant/labor
   - 状态：试用期/在职 → probation/active（默认 在职）
   - 参加社保：是/否 → true/false
   - 公积金比例：Excel 填百分数（如 12）→ 存 0.12（Decimal(4,2) 实读 schema 确认精度后转换）
   - 日期：一律 `YYYY-MM-DD` 字符串解析，非法日期报行错误
6. **不做清单**：不迁移 workHistory / certificates（JSON 字段，README 注明需系统内补录）；不建用户账号（userId 留空，上线后由 HR 逐个开通）；不自动创建部门（部门代码不存在 = 行错误，README 说明需先在组织模块建部门）；不做用户账号/薪资方案/社保参保登记等关联档案（一期真实迁移只迁员工主档，其余 HR 上线后补——README 写清楚边界）。

2. **`员工档案迁移样例.xlsx`**（合成自测数据，同样表头）：**40 行全合法**，工号 `XACH20990001`~`XACH20990040`，姓名 `迁移测试01`~`迁移测试40`，部门代码 PEDU/HR/FIN/TECH 轮换，入职日期/合同/社保等字段填充合理合成值（身份证可用 `11010119900101xxxx` 号段合成），其中 5 行走`试用期`状态
3. **`员工档案迁移错误样例.xlsx`**：5 行各含一种典型错误（缺工号 / 部门代码不存在 / 日期非法 / 枚举值非法如性别填"未知" / 工号与已有员工重复 `XACH20260001`），用于演示校验报告

### 4.3 `server/scripts/migration/import-employees.ts`（新增）

CLI 参数（用 `process.argv` 手工解析即可，不引新依赖）：

```
pnpm --filter hrms-server migration:employees -- --file output/员工档案迁移样例.xlsx [--company XACH] [--dry-run] [--purge-test-data]
```

流程：

1. **读文件** → 表头与模板列名逐一对齐（列名不匹配报清晰错误）
2. **校验**（所有行跑完再报）：必填缺失 / 部门代码查库不存在 / 枚举非法 / 日期非法 / 手机号格式（11 位数字）/ 身份证格式（18 位）/ 工号格式（符合 configs 规则前缀或至少非空唯一）/ 文件内工号重复 / 工号已存在于库（查重仅提示"将跳过"不算错误）
3. **dry-run**：只输出「N 行合法 / M 行错误 / K 行将跳过」+ 错误明细，**不写库**
4. **正式导入**：逐行 createEmployee + 工号回写（§3.3 事务策略）；行失败不中断整体，记录继续；末尾输出「成功 X / 跳过 Y / 失败 Z」+ 失败明细
5. **报告落盘**：`output/import-report-<yyyymmdd-hhmmss>.json`（每行：行号、工号、姓名、结果、原因、生成的员工 id）
6. **`--purge-test-data`**：硬删除工号前缀 `XACH2099` 的所有员工（`prisma.employee.deleteMany`，注意先删会阻塞的关联——实读 schema 关系，如有 EmployeePositionHistory 等关联先删子表）；**安全措施**：只接受此前缀，硬编码白名单，不接受任意前缀参数。purge 后输出删除条数
7. 退出码：有行失败或校验错误 = 1，全成功/全跳过 = 0

## 5. 关键决策点

### 5.1 工号保留的事务策略

§3.3 给了两种方案（$transaction 包裹 / 补偿回滚）。实读 createEmployee 内部是否已含事务后选型，结论+理由写进报告。

### 5.2 样例数据的真实性

合成样例要"像真的"：日期范围合理（入职 2020-2026）、合同类型以正式为主、社保基数 4000-25000 区间——这样校验逻辑才能被真实触发。但姓名/工号必须明显是测试数据（`迁移测试xx` / `XACH2099xxxx`）。

### 5.3 xlsx 库的已知坑

`xlsx@0.18.5` 在 ESM/tsx 下 `import * as XLSX from 'xlsx'` 可用；日期单元格可能返回序列数（`cellDates: true` 选项或 `XLSX.SSF` 处理）——实读解析结果后决定，把处理方式写进报告。中文文件名路径在 Windows 下无问题。

### 5.4 执行器环境红线（Windows + opencode 沙箱，血泪教训）

**任何一条命令/工具调用被沙箱拒绝 = 整个任务立即中止**（已发生 3 次）。只允许朴素命令：
