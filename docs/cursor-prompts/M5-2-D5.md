### 3.2 RBAC 权限矩阵（已实读 `server/src/constants/permissions.ts` 五角色分配）

| 权限点 | admin | hr | dept_head | executive | employee |
|---|---|---|---|---|---|
| `salary-adjustment:read` | ✅(通配) | ✅ | ✅ | ✅ | ✅ |
| `salary-adjustment:write` | ✅ | ✅ | ❌ | ❌ | ❌ |
| `salary-adjustment:approve` | ✅ | ❌ | ❌ | ✅ | ❌ |

| `promotion:write` | ✅ | ✅ | ❌ | ❌ | ❌ |

| `pip:write` | ✅ | ✅ | ❌ | ❌ | ❌ |
| `pip:review` | ✅ | ✅ | ❌ | ✅ | ❌ |

**反直觉点（必须严格遵守）**：

1. **提议/审批分离**：调薪提议只能 **hr** 发起，审批只能 **executive** 做——hr 无 approve、executive 无 write。同一人不能既提议又审批（页面上两个操作永远不会同时出现）
2. **PIP 评审 = hr + executive**（dept_head 无权评审）
3. **dept_head 全只读**（3 个 read）
4. **employee 有 3 个 read 但后端无数据隔离**（已实读：三个 list service 均**无** isEmployeeOnly 过滤，与 D4 commission 列表不同）→ 前端 ESS 视角**强制按本人 employeeId 过滤**（沿用 D3 PayoutList 模式），后端隔离缺口写入「已知问题」留 M5-04 安全加固

### 3.3 存储结构（已实读，前端类型设计的决定性事实）

| 对象 | 存储 | 列表 item 形态 |
|---|---|---|
| 调薪提议 | **audit_logs**（action=`SALARY_ADJUSTMENT_PROPOSE`） | item = 审计日志行：`id`（即审批用的 :id）、`createdAt`，业务字段在 **`newValue` JSON** 里：`{ employeeId, period, evaluationQuarters, sRatio, aRatio, adjustmentRate, totalRecords, approvalStatus }` |
| 调薪审批 | **新增一条审计日志**（action=`SALARY_ADJUSTMENT_APPROVE/REJECT`，resourceId=原提议日志 id） | 审批状态派生：存在引用原日志的审批日志即已审批（后端 72903 防重） |
| 晋升提名 | **audit_logs**（action=`PROMOTION_PROPOSE`） | 同上，字段在 newValue；资格门槛：≥2 个 A 或 1 个 S（72905） |
| PIP | **真实表** `performance_pips`（**含 reviews 数组**，评审在 `performance_pip_reviews`） | 扁平实体：id/employeeId/startDate/endDate/status/reason/outcome?/triggeredBy/createdAt + reviews[{ id, reviewMonth, reviewDate, rating, comment?, reviewerId, createdAt }] |

**含义**：调薪/晋升列表的展示与筛选要围绕「审计日志行 + newValue payload」设计（员工 id 在 `newValue.employeeId`，创建时间用 `createdAt`）；PIP 是常规实体表格。**两类形态不要混用**。动笔前实读 3 个 service 的 list 返回，把逐字段结论写进交付报告（§5.1）。

### 3.4 错误码

72901 调薪记录不存在 / 72902 period 格式 / 72903 已审批 / 72905 晋升资格不满足 / 72907 已有进行中 PIP / 72908 连续 D 档不满足。前端统一走 http 封装错误提示，业务侧对 72905/72908 这类资格错误直接展示后端 message 即可。
