## 4. 实施任务（4 个缺陷 + E2E 还原）

### 4.1 缺陷 1：绩效列表响应信封错位（server 修，高优先）

- **根因**：`server/src/controllers/performance.controller.ts` 的 cycles/indicators/schemes 三个 list 端点（起草时在第 40/68/88 行）用 `res.json({ success: true, ...result })` 扁平返回；而项目约定是嵌套信封（参照 `employee.controller.ts` 列表端点 `{ success: true, data: ..., ... }`），client `unwrapPerformancePage`（`client/src/api/types/performance.ts` 约 269 行）读 `envelope.data.items`——导致绩效三个列表页永远「共 0 条」。
- **修法**：三处改为 `{ success: true, data: result }`（先实读 service 返回结构确认 result 含 items/total/page/pageSize，与 client 期望对齐；若字段名不匹配以 client unwrap 实读为准调整）。
- **测试**：grep `performance` 相关 controller/route 测试，把断言扁平形态的用例最小化改为嵌套形态并加注释 `// M5-09: 信封对齐项目约定`。
- **E2E 还原**：`e2e/specs/05-performance.spec.ts`——三个列表页改为直接 UI 断言新建条目可见（去掉「API 直连校验 DB」的降级旁路与 `page.evaluate` 注入 form 字段的 hack；若 el-select 下拉空的问题因列表修复而消失则恢复正常操作，未消失则保留注入并在报告说明）。

### 4.2 缺陷 2：web 端打卡必败（client 修，选型已定：改 GPS）

- **根因**：`client/src/views/attendance/attendance/AttendanceList.vue` `onClock()` 硬编码 `clockType:'wifi'` 但不发 `wifiSsid`；server `attendance.service.ts`（约 355 行）对 wifi 强校验 `wifiSsid ∈ configs attendance.wifi_ssids`，否则 71903。浏览器无法读取 WiFi SSID，此路永远不通。
- **修法（已定，照做）**：web 端打卡改为 **GPS 模式**——用浏览器 Geolocation API 取坐标，提交 `clockType:'gps'` + 经纬度（字段名实读 server `ClockInInput` 的 gps 分支与 client `clockIn()` API 类型，缺字段则补类型定义）。实读 server gps 校验段（约 365 行起）确认依赖的 configs 键（办公坐标/最大距离），若 seed 无这些 config 则在 seed 的 attendance 配置段补上合理默认值（西安办公点坐标可先用近似值并注释「需行政确认真实坐标」），同时给当前库写订正脚本（§3.3）。
- **降级处理**：定位被拒/超时时 ElMessage 提示「请允许浏览器定位后打卡」，不静默失败。
- **E2E 还原**：`e2e/specs/02-attendance.spec.ts`——去掉 `page.route` mock，改用 Playwright `context.grantPermissions(['geolocation'])` + `context.setGeolocation()` 设置为 configs 办公坐标，真实走通打卡 → 断言新记录出现。坐标值从 README/seed 实读保持一致。

### 4.3 缺陷 3：请假审批流模板 key 不匹配（seed + 订正）

- **根因**：seed.ts（约 381 行）写入 config `leave.approval_flow_short = 'leave:leave_short'`，指向不存在的模板；而 seed（约 1330 行）实际创建的审批流 key 是 `leave_default`（`approval.service.test.ts` 也以 `leave:leave_default` 为准）。
- **修法**：seed 的 config 默认值改为 `'leave:leave_default'`（先实读 leave.service 确认它读的 config category/key 全名与拼接规则）；按 §3.3 写订正脚本更新当前库 configs 行并执行（注意 configs.value 是 JSONB，订正 SQL/脚本注意 JSON 字面量）。
- **E2E 还原**：`e2e/specs/03-leave.spec.ts`——提交断言从「成功跳列表/错误 toast 双路径」升级为单路径：提交成功 → 列表可见且状态为待审批/审批中（以 seed 审批流实际首环节为准，实读后写死断言）。

### 4.4 缺陷 4：算薪前置档案缺失（seed 补齐）

- **根因**：`payroll_calculation.service.ts` 对无 active 薪资方案/社保参保登记的员工抛 73408；seed 的 5 名员工均无这两类档案，导致「发起算薪」必败。
- **修法**：seed.ts 增补「seed 员工薪酬档案」段（ensure 语义）：为 5 名 seed 员工各建一条 active `EmployeeSalaryPlan` + `EmployeeInsuranceRegistration`（实读这两个 model 的必填字段与关联——薪级薪档/社保方案若需前置记录则一并 ensure，金额用整数千位示例值并注释「演示数据」）。
- **E2E 还原**：`e2e/specs/04-payroll.spec.ts`——从「可达 + 双路径」升级为全链路：发起算薪（含 admin 在内至少 1 人算出）→ 执行 → 状态机推进到可达最远环节 → 工资单列表可见 admin 工资单。若状态机某环节因其他配置缺失走不通，按提示词通用降级规则缩减并在已知问题写明。
