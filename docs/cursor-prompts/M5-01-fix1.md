# M5-01-fix1 修订任务（opencode headless）—— BullMQ Redis 连接配置修复

M5-01 真实联调冒烟发现**后端启动即崩溃**：`BullMQ: Your redis options maxRetriesPerRequest must be null`（`server/src/jobs/notification.queue.ts:157` 的 `new Worker` 触发）。这是本切片的正收益——请只修复这一个问题，不做任何其他改动。

## 根因（已实读确认）

- `server/src/lib/redis.ts` 第 5-15 行：共享 `redis` 客户端配置 `maxRetriesPerRequest: 3`
- BullMQ 的 Worker（阻塞连接）**强制要求** `maxRetriesPerRequest: null`（另建议 `enableReadyCheck: false`）
- `notification.queue.ts` 的 `new Queue`（40 行）与 `new Worker`（157 行）都直接复用了这个共享客户端

## 修法（按此执行）

1. `server/src/lib/redis.ts`：新增导出工厂函数（**不改动共享 `redis` 客户端的既有配置**，缓存等其他用途不受影响）：

```ts
/** BullMQ 专用连接：Worker 阻塞命令强制 maxRetriesPerRequest=null（与共享缓存客户端隔离） */
export function createBullMqRedis(): Redis {
  return new Redis(env.REDIS_URL, {
    maxRetriesPerRequest: null,
    enableReadyCheck: false,
  });
}
```

2. `server/src/jobs/notification.queue.ts`：`new Queue` 与 `new Worker` 的 `connection` 改用 `createBullMqRedis()`（Queue 与 Worker 各持一条独立连接；删除对共享 `redis` 的 import 若不再使用——`connectRedis()` 调用若仅为 BullMQ 服务可一并移除，若有其他用途则保留）

3. 检查 `server/src/jobs/notification.queue.ts` 与 `redis.ts` 的既有测试（`*.test.ts`）：如有断言共享连接配置的用例需同步；如无则 0 改动。**禁止修改其他任何测试。**
