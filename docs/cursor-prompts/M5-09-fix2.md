## 三、限流结构修正（fix2 核心，commit bf53745）

### 原实现缺陷

`apiLimiter` 全局挂在 `app.use(apiLimiter)`（authenticate **之前**）→ `req.user` 永不注入 →
user-tier `keyGenerator` 恒退回 IP → **user-tier 形同虚设**，单用户可占满整个 IP 配额（300/min）。
用户拍板（2026-09-02）的"用户 300/min + IP 3000/min"语义**从未真正生效**。

### fix2 拆两段（阈值不变，语义落地）

```text
ipLimiter   3000/min  key=ip    app.ts 全局 app.use(ipLimiter)    —— 未认证 flood / 共享出口兜底
userLimiter  300/min  key=userId  auth.ts authenticate 内 jwt.verify 成功后串联 —— 已认证按人隔离
loginLimiter 10/5min + refreshLimiter 30/min 独立挂载（不变）
```

改动的文件：
- `server/src/middleware/rate-limit.ts` — 拆出 `userLimiter` / `ipLimiter`；`apiLimiter` 保留但 @deprecated
- `server/src/app.ts` — 全局 `app.use(apiLimiter)` → `app.use(ipLimiter)`
- `server/src/middleware/auth.ts` — `authenticate` verify 成功后调 `userLimiter(req, res, next)`
  （自动覆盖全部走 authenticate 的业务路由 + /auth/me、改密等，无需改 22 个 route 文件）

### 为什么不再 429（量化）

| 指标 | 值 | 配额 | 结论 |
|---|---|---|---|
| 单用户请求率 | ~10 req/min | user 300/min | ✅ 余 30 倍 |
| 共享 IP 总流量 | ~1000 req/min（sustain 峰值 ~36/s=2160/min） | IP 3000/min | ✅ 余 1.4 倍 |
| 实测 | 4000 请求全 200 | — | ✅ 0 个 429 |

## 四、压测模型修正（fix2）

### 根因（两个叠加）

1. **压测负载 ≠ PRD 语义**：PRD §8.1「并发能力 ≥100 用户」= 100 个在线用户的人类操作节奏；
   旧 yml `sustain arrivalRate: 100` = 每秒 100 个一次性 VU = **100 req/s 洪水（6000/min）**，
   任何配额都打爆。
2. **单 admin token 身份受限**：全部 VU 共用 1 个 token → 即使配额正确也受单用户 300/min 限制。

### 修复

1. **token 池化**（`server/scripts/fixes/m5-09-token-pool.mjs`）：DB 建 100 个压测用户
   （`perf_0001..perf_0100`，角色 admin，不绑员工档案）+ 用 server `JWT_SECRET` **直签 100 个 token**
   （与 `auth.service.signAccessToken` 同 payload 结构，绕过 loginLimiter 5min/10 次）→
   `loadtest/.auth/token-pool.json`。`processor.mjs` beforeScenario 按轮询游标取池中 token
   （每 VU 全程同一身份），池缺失时 fallback 单 admin token。
2. **负载模型**（`load-test.yml`）：ramp 20s × 5/s = 100 VU 进入；每 VU `loop [GET + think 6s] count 20`
   （存活 ~120s，同一 VU 模拟同一用户持续操作）；sustain 100s × 1/s 补位。
   实际曲线：峰值 ~36 req/s，平均 11 req/s —— 真实反映"100 人日常使用"且留足配额余量。
