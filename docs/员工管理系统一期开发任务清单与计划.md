## 一、AI Coding 开发原则

本项目采用 AI Coding 模式（Kimi Code / Cursor / Copilot Workspace 等），与传 统人工开发相比有以下特性，任务拆分必须适配：

特性| 对任务拆分的要求| 具体做法  
---|---|---  
上下文窗口有限| 每个任务的上下文必须自包含| 每个任务附带"上下文包"：相关 PRD 章节 + 数据模型 + 接口契约 + 现有代码引用  
擅长小步迭代| 任务粒度 ≤ 一个会话能完成| 单任务 ≤ 200 行核心代码 / ≤ 2 小时 AI 生成量；大功能拆成"模型→迁移→服务→接口→页面"5 步  
容易"看着对、其实错"| 测试必须前置且可机械校验| 每个任务带 acceptance criteria（API 响应示例 / SQL 校验 / 页面截图点）  
风格易漂移| 强结构化约定 + 复用现有模板| 复制招聘系统的目录结构、ESLint 配置、Prisma 模板、Vue 组件库  
不擅长跨文件一致性| 显式声明依赖关系| 每个任务标注"前置任务"和"被依赖任务"，避免并行冲突  
对领域规则易遗漏| 业务规则显式化、配置化| 薪酬/绩效/考勤规则全部走配置表，不写死在代码里  
重构能力强| 先跑通再优化，不一开始追求完美| 一期先垂直切片（一个模块端到端跑通）再横向扩展  
  
## 二、整体分期策略

### 2.1 阶段划分

阶段| 周期| 核心目标| 交付物  
---|---|---|---  
**M0 脚手架**|  第 1 周| 项目骨架 + 基础设施| 可登录、可连库、可部署的空壳系统  
**M1 组织人事**|  第 2-4 周| 模块 A 完整落地| 组织架构 + 员工档案 + 入转调离 + 合同管理可用  
**M2 考勤假勤**|  第 5-7 周| 模块 B 完整落地| 打卡 + 排班 + 请假/加班/出差 + 月度汇总可用  
**M3 绩效管理**|  第 8-10 周| 模块 D 完整落地| KPI+OKR 考核 + 系数配置 + 五档评分可用  
**M4 薪酬核算**|  第 11-14 周| 模块 C 完整落地| 自动核算 + 社保三地 + 个税 + 工资条可用  
**M5 联调上线**|  第 15-17 周| 集成测试 + 数据迁移 + 试运行| 正式上线  
  
总计 17 周（含 2 周并行试运行）。M3 绩效在 M4 薪酬之前，因为薪酬依赖绩效系数。

### 2.2 垂直切片策略（关键）

不采用"先全部后端再全部前端"的横向切法，而是按**垂直切片** （每个切片包含 模型→API→页面 完整链路）：

  * 每个切片独立可演示、可测试
  * AI 单次会话能完成一个切片
  * 失败影响面小，回滚成本低
  * 早期就能让 HR 看到真东西，及时纠偏

B6| 月度考勤汇总（含员工确认 + HR 锁定）| 3d  
  
### 5.2 关键约束

  * GPS 打卡必须记录经纬度 + 地址反解析（腾讯地图 API）+ 拍照上传（可选，二期）
  * 假期额度计算放在 service 层单独函数 `calculateLeaveBalance(employeeId, leaveType, year)`，便于单元测试
  * 考勤异常识别用**定时任务** （node-cron 每日 02:00 跑），不在打卡接口里实时算
  * **考勤数据导入模块按得力 e+ 导出格式做解析模板**（人员/日期/设备/打卡时间字段映射），二期接 API 时解析与入库逻辑直接复用，仅替换数据源。
  * 导入与计算解耦：导入只负责把打卡原始记录入库（`attendance_records`，标记 source=导入），排班/请假/加班规则计算独立运行，便于二期叠加 API 来源数据。

### 5.3 得力适配器（一期可选尾巴）

  * 范围：若得力 e+ 接口授权（App-Key/Secret）在一期期间提前就绪，可顺带实现「得力适配器」——自动同步部门/员工与打卡数据，替代手工导入。
  * 不阻塞主流程：作为可选尾巴，授权未到位则不实现，一期仍以手工导入闭环交付。
  * 复用：适配器复用 B2 导入的「解析→入库」逻辑，仅将数据源从 Excel 换成 API 拉取（定时任务分页拉取 + 限频保护）。
  * 前置动作：得力接口授权采购（得力 e+ App → 服务 → 考勤机 → 考勤接口）列为**二期前置、本期即可启动**，避免二期开始时排队等待。

  * 敏感字段是否加密（身份证、银行卡、薪资）
  * 审计日志是否记录（增删改操作）
  * SQL 注入 / XSS / CSRF 风险
