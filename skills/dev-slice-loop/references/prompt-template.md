# 切片提示词模板与起草原则

提示词质量是这个工作流的命脉：agent 无人值守、无澄清环节，提示词必须自足。以下骨架在 40+ 个切片上验证过（Cursor/Cursor-headless/dsh/opencode/Codex 通用）。

## 起草铁律（审核者侧，最重要）

1. **全部事实实读核实**：API 路径、HTTP 方法、权限点、返回结构、既有工具函数——全部先读真实代码再写进提示词，禁止凭记忆/猜测。读不到的就在提示词里设「关键决策点」让 agent 先读再动笔（见 §5 节模式）
2. **文件预算精确到个数**：「本切片必改 N 个文件」，逐一编号列出；清单外文件一律禁止
3. **反直觉点显式标注**：权限与直觉不符的地方（如「校准接口用 record:read 而非 grade:calculate」）必须写进权限矩阵，否则 agent 会「自作主张修正」
4. **基线数字写死**：当前测试数、lint 状态等验收基线先自己跑一遍再写进提示词
5. **提速约定**：agent **不跑验收命令、不 git commit**——验收由审核方重跑。这能把每轮耗时砍掉 1/3 以上，且 agent 自报的「测试通过」本就不可信

## 章节骨架

```markdown
# <切片ID> <标题> 执行提示词

## ⚠️ 强约束（最优先阅读）
（3-8 条：禁改后端 / 禁改 package.json / 文件预算 N 个 / 不跑验收不 commit /
 编码红线——禁整文件重写、UTF-8 无 BOM / headless 无人工确认，直接动手）

## 1. 任务 ID + 目标
### 1.1 任务 ID
### 1.2 任务目标（一段话）
### 1.3 端点清单（0 新增后端端点 / 列出全部要消费的端点 + 方法 + 权限点）

## 2. 上下文
### 2.1 项目位置
### 2.2 当前状态 + 必增文件清单
### 2.3 可复用模块（严禁重写——列出既有工具函数/组件/类型及位置）
### 2.4 业务规则来源（写类型前必读的文件列表）

## 3. 必读约束
### 3.1 代码范式（项目既有模式，给 1 个参照文件）
### 3.2 命名规范
### 3.3 RBAC 权限矩阵（已实读，逐角色列出本切片相关权限点）
### 3.4 错误码 / 审计 / 配置化约定

## 4. 实施任务
### 4.x <文件名>（新增/仅追加/条件修改）—— 每个文件一节，说清做什么、不做什么

## 5. 关键决策点（详尽）
### 5.1 响应结构确认（最优先：让 agent 先读 service 源码确认返回结构，再写类型）
### 5.x 其他决策点……
### 5.y 执行器环境特注（headless 注意事项）
### 5.z 不做清单（明确排除项，防范围蔓延）

## 6. 修改文件清单
### 6.1 必改文件（N 个，逐一编号）
### 6.2 禁止修改文件（清单以外一切）
### 6.3 越界检测（交付时自检命令：git status 必须只出现 6.1 的文件；git diff --stat server/ 必须 0 行……）

## 7. 验收标准
### 7.1 硬性验收（审核方执行，你不跑；仅供了解通过线：基线数字写死）
### 7.2 交付报告模板（agent 的最终回复必须完整包含：完成范围/端点消费/新增文件/
修改文件逐行说明/主动识别与处理/测试/已知问题/红线自检）

结尾：「按本提示词直接执行（headless 环境无人工确认环节）：先输出实施计划，然后动手，
最终回复给出完整交付报告。」
```

## 条件修改条款（推荐模式）

允许 agent 修改清单外某个文件的唯一方式：在提示词里预先授权「条件修改」——写明触发条件、要求最小化改动、必须加注释说明原因、必须在交付报告中逐行列出。示例：路由追加导致既有测试的计数断言失效时，授权更新断言并注释。（先例：D2 切片 agent 主动识别 children 断言冲突，经评审接受为合理行为。）

## 修订提示词（fix 轮）模板

修订提示词要**小而狠**，只列问题不给发挥空间：

```markdown
# <切片ID>-fixN 修订任务（<执行器> headless）

<切片ID> 的代码已写完，审核发现 **N 个问题**，请只修复这 N 处，不做任何其他改动：

1. `<文件>` 第 X 行：<问题> —— <推荐修法>
2. ……

**编码红线**：只做外科式小编辑，禁止整文件重写（防 BOM/行尾污染）。
**禁止**：修改其他任何文件 / git commit / 运行测试套件（审核方会重跑）。

完成后，最终回复列出：改了哪几个文件、每处改动的 diff 摘要。
```

实测：修订轮通常 4-5 分钟完成，收敛极快（opencode 2 轮、Codex 1 轮即全绿）。
